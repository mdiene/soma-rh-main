- **Branche** : `feat/road-04-sauvegarde` · **Phase** : 1 · **Dépend de** : ROAD-03 (la clé et le chiffrement des sauvegardes ne doivent pas être conçus deux fois) ; aucune migration attendue, mais l'agent reste dans la file `soma-base`
- **Partie propriétaire** : choix du second stockage et gestion de la clé de sauvegarde.

## Objectif
Sauvegarde `pg_dump` quotidienne chiffrée (`age` ou `gpg`) vers un second support, conservation 30 jours / 12 mois, restauration testée dans une base jetable, résultat journalisé. Règle 3-2-1 visée (§3.3 du document maître).

## Fichiers concernés
`scripts/local-backup.ps1`, `scripts/local-restore.ps1`, `scripts/supabase-backup.ps1` (étendre, ne pas dupliquer) ; nouveau script de test de restauration ; `docs/` : procédure écrite (poste de secours local inclus).

## Critères d'acceptation
- Une **restauration complète réussie et chronométrée** (durée relevée, à comparer à l'objectif RTO 4 h), journalisée.
- Sauvegarde déclenchée par planification (tâche planifiée Windows ou équivalent documenté), pas seulement à la main.
- Fichiers chiffrés ; clé hors dépôt ; purge selon la rétention.
- Procédure de reprise écrite pour la version locale comme poste de secours.
- Vérification de si le plan Supabase propose la restauration à un instant donné : constat noté, à confirmer avec le propriétaire.

## Contrôles à lancer
Restauration sur base jetable puis `scripts/test-sql.ps1` et `scripts/verify-payroll.ps1` sur la base restaurée (comparaison avec l'originale) ; `scripts/scan-pii.sh` ; revue `ecc:security-reviewer`.

## Interdits
Sauvegarde non chiffrée laissée dans le dépôt ou dans un dossier synchronisé ; restauration sur la base de travail ; clé ou chemin secret commités.
