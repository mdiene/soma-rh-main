Ce plan détaille le prompt. Chaque phase produit un rapport `NN-*.mdx`, des tests rejouables et un commit. Une phase n'est « terminée » que si son critère de sortie est vérifié.

## Étapes détaillées par phase

### Phase 1 : exigences et registre légal
1. Extraire les rôles et droits depuis les politiques RLS réelles (`pg_policies`), pas depuis la documentation.
2. Dresser le catalogue des 17 UC minimum et leurs acteurs.
3. Relier chaque invariant I1-I20 à une exigence, une règle légale (`RL-xxx`), un UC et un test T-Ix.
4. Recherche web des règles : IR (barème, parts), TRIMF, IPRES général et cadres, CSS, CFCE, heures supplémentaires, préavis, indemnités, congés, SMIG. URL, article et date notés ; sinon « à confirmer ».
5. Comparer chaque règle à la valeur en base (`payroll_settings`, `tax_slabs`) : statut conforme, écart ou à confirmer.

### Phase 3 : usine de données
1. Générateur TypeScript déterministe dans `tests/fixtures/qa/`, graine fixe, noms fictifs, matricules `QA0001…`.
2. Scénarios `pme-25`, `pme-80`, `eti-200`, `grande-1000`, chargés par `scripts/qa-reset-scenario.ps1 -Scenario nom`.
3. Comptes de test par rôle avec mot de passe jetable lu dans l'environnement, jamais commité.
4. Avant chaque rechargement : sauvegarde, entrée dans `registre-donnees-de-test`.
5. Installer Playwright (Chromium d'abord ; Firefox et WebKit si le téléchargement aboutit).

### Phases 4 à 6 : tests
1. Oracle indépendant dans `tests/oracle/`, écrit depuis le registre légal, sans lire le PL/pgSQL.
2. Comparaison différentielle sur plusieurs milliers de cas ; chaque écart tranché d'après le texte.
3. Tests SQL par rôle avec `set local role` et JWT simulé, dans des transactions annulées.
4. Tests de concurrence : deux sessions `psql` simultanées sur le même traitement.

### Phases 7 à 9 : qualité non fonctionnelle
1. Chronométrer calcul, livre de paie, planning et analyses sur les quatre scénarios ; `EXPLAIN ANALYZE`.
2. Contrôles de sécurité en SQL versionné dans `tests/sql/` ; `npm audit` ; ports Docker.
3. axe via Playwright sur les pages principales.

### Phases 10 à 13 : pérennisation
1. Étendre `ci.yml` par étapes, chaque étape ajoutée seulement quand elle passe en local.
2. Recette en français courant, journal des défauts, test de restauration chronométré.
3. Benchmark : partir de `ANALYSE_SAGE_PAIE_RH_VS_SOMA_RH` et le vérifier avec les résultats.

## Limites assumées

- Outils absents (k6, OWASP ZAP, Snyk, WebKit, `mint`) : installation tentée, sinon étape marquée bloquée.
- Aucun chiffre légal n'est modifié dans le moteur sans source datée et décision du propriétaire.
- Les analyses de montée en charge sont mesurées sur cette machine, pas sur un serveur de production.
